# 设备语音下单冰淇淋

接口依据《创梦龙-冰淇淋制作HTTP接口.md》。端到端和级联共用同一个 HTTP 动作服务，不影响小程序测试页。

## 配置与网络

在运行 backend 的环境中配置：

```dotenv
ICECREAM_ENABLED=true
ICECREAM_DEVICE_SN=VI-ESP32S3-68EE8FC60B38
ICECREAM_IP=
ICECREAM_PORT=8080
ICECREAM_USERNAME=chuangmenglong
ICECREAM_PASSWORD=填写接口文档的登录密码
ICECREAM_QUERY_TIMEOUT_SECONDS=5
ICECREAM_EXECUTE_TIMEOUT_SECONDS=10
ICECREAM_POLL_INTERVAL_SECONDS=1.5
ICECREAM_MONITOR_TIMEOUT_SECONDS=300
```

IP 暂时留空，不会发送 HTTP 请求；指定设备会播报尚未配置。填 IP 后需要重启本地后端，Docker 需要重新创建 backend 容器才能加载新的环境变量。示例文件不保存真实密码。

请求由 backend 发出。现场的语音设备连接 Wi-Fi，不能让云端 backend 自动访问现场 IP。后端必须在现场运行，或通过 VPN 等连接现场内网；Docker 容器也必须能访问该地址。不建议把这个 HTTP 控制端口直接暴露到公网。Wi-Fi 密码属于设备网络配置，不是这个 HTTP 接口的登录密码。

仅本轮加载的 `device_sn` 与配置中的单个 SN 完全相等才进入匹配和调用。其他 SN 不登录、不下单、不参与状态播报。

## 语音匹配

在 ASR 完成后对本轮文本做整句匹配，不根据知识库、记忆或模型生成的文字下单。支持一杯、一个、一份、数字 1，以及“冰激凌”的写法，例如：

- 帮我下单一杯冰淇淋
- 我要一杯冰淇淋
- 来一杯冰淇淋
- 给我来一杯冰淇淋
- 请帮我点一杯冰淇淋
- 我想买一杯冰淇淋
- 帮我做一个冰淇淋
- 帮我订一份冰淇淋
- 给我一杯冰激凌

“不要给我一杯冰淇淋”“如果我要一杯冰淇淋”“他说我要一杯冰淇淋”“冰淇淋多少钱”不会调用制作接口。两杯或其他数量会提示一次只能制作一杯，不会擅自改成一杯下单。

可主动问“我的冰淇淋做好了吗”“冰淇淋好了没”“查询冰淇淋状态”，这些只查询，不下单。

## 下单与状态播报

1. 登录获得 token，查询当前是否有工作流在运行。
2. 空闲时发送 `POST /api/workflows-json/make-icecream/execute`，请求体 `{}`。
3. 成功返回只播报“机器已受理，正在确认制作状态”，不表示已做好。
4. 后台每 1.5 秒查询 `/api/workflows-json/instances`，排除下单前已有的实例 ID，首次看到新 `make-icecream` 时跟踪该实例。
5. `RUNNING` 首次出现时播报制作中；`COMPLETED` 播报完成可取；`FAILED` 播报失败。相同状态不会反复播报。
6. 该语音轮次在最终状态播报完毕后发送 `dialogue.done`。等待过程中不能在这条连接上开启另一轮语音；仍可取消对话。

端到端状态播报沿用同一个千问会话、当前模型和音色，以及现有 PCM 到 CI MP3 的链路。制作动作已经由后端执行；模型仅朗读已确认的状态文本，不负责决定下单或制作成功，也不检索知识库或联网。级联状态播报沿用百度 TTS。

只将真实用户请求和实际播报合并保存为本轮问答，状态播报不会伪造新用户消息。普通聊天继续使用原有记忆、知识库和联网链路，下一轮恢复正常配置。

## 超时、重登与边界

- 明确返回 401：重新登录，然后重试该次请求一次。
- 制作请求超时、断连或结果格式异常：不能确定是否已受理，继续查询，绝不自动重发制作请求。
- 默认 300 秒未确认最终状态：播报结果未确认，并保留未确认状态，后续下单先查询，不盲目重下单。
- 语音取消或断开：只停止该连接的播报，不取消已经受理的机器任务；后台仍查询结果。重新连接后可主动查询状态。
- 后端进程重启会丢失本进程的 token 和跟踪状态，下一次请求会重新登录并查询机器。接口没有幂等键，也没有在执行响应里返回实例 ID，因此不能承诺跨进程重启、外部同时调用情况下的严格一次执行。现场先按现有单进程 backend 部署测试。
- 这次没有新增数据库表、依赖或迁移。单进程锁用于防止同一进程里的重复并发下单，机器仍以 `PARALLELISM_REJECT` 保证同一时刻单杯制作。

## 测试

`tests/test_icecream.py` 使用模拟 HTTP 和模拟语音上游，验证 SN 精确匹配、否定句、数量限制、登录与 401 重登、受理与完成区分、实例跟踪、失败/超时播报、不重复 POST、语音取消以及两条设备语音链路。没有调用真实机器或真实模型。

现场需要验证网络可达、登录、单杯制作，以及 ESP32 在制作等待期间是否保持当前播放会话。若固件自身有短时间播放超时，需要配合调整；后端模拟测试不能验证真机播放器的等待行为。

千问续播沿用官方客户端事件的 `session.update` 和 `response.create`，见 [阿里云客户端事件文档](https://help.aliyun.com/zh/model-studio/client-events)。
